# 领域知识图谱 — code-time-tracker-vscode

本目录是本项目的**领域优先知识库**，由 **AGENTS.md R29** 治理。五件套定义与红线见 R29，此处不重复。

> **为什么先做领域而不是 RAG**：检索解决的是「从资料中找出可能相关内容」，并不解决
> 「AI 是否已拿到做出完整工程判断所需的知识集合」。固定结构提供的是**知识覆盖约束**——
> 它告诉 AI「解决这类问题至少要理解哪些方面」；检索只能告诉 AI「这里有一些可能相关的资料」。
> 骨架没立起来，检索再快也换不来稳定的系统理解。RAG 在这里的定位是**长尾补证**：
> 结构里缺的细节去检索原始文档，确认后**回写**到结构里。

## 一、渐进式披露：四层阅读路径

**不要一次读完。** 每层只加载完成当前判断所必需的知识，下一步由前一步的结论触发。

| 层 | 要回答的问题 | 本项目对应 | 迭代频率 |
|---|---|---|---|
| **业务层** | 为什么改？需求里的词在技术系统里对应什么？ | [`projectbrief.md`](../projectbrief.md) + 各领域 `meta.md` 的元语表 | 低 |
| **架构层** | 涉及哪些系统？影响谁？链路怎么走？ | `server-api` / `sync-client` 的契约与链路 + [`systemPatterns.md`](../systemPatterns.md) 体系图 | 中 |
| **系统层** | 这个模块怎样改才安全？ | 本仓库代码与配置 + `systemPatterns.md` + 领域 `principles` / `scenarios` | 高 |
| **基建层** | 工程底线与上线规则是什么？ | AGENTS.md R6/R7/R9/R17/R20 + `ai-workflow` + `.gitmessage` / `.editorconfig` | 很低 |

**典型路径**：需求 →（业务层）元语消歧 →（架构层）定位链路与归属 →（系统层）读契约与代码 →
（基建层）确认提交与版本规则。

**不要跳层**：从「系统层」直接下手是最常见的失败模式——在没确认「需求说的是什么」之前
grep 代码，会把同名不同义的概念混在一起，方案从第一步就偏了。

## 二、事实回源：不同事实回不同源

**没有单一资料源是可靠的。** 每类事实有唯一权威来源，冲突时按下表裁决：

| 事实类型 | 权威来源 | **不作数** |
|---|---|---|
| ctt-server 当前行为 | `../ctt-server` **源码** | 它的文档与 memory-bank（已发现 8 处不一致） |
| 本地库 schema | `../code-time-tracker` 的 `database/MigrationManager.kt` | 本仓库的转述 |
| 统计口径 | ctt-server `StatsCalculator` + 插件端显示语义 | 文档里的口径描述 |
| 本仓库当前行为 | 本仓库代码 + 配置 | 记忆文件 |
| 产品意图与取舍 | **用户确认过的结论** | 代码现状、旧文档 |
| 历史原因 | 领域 `practices.md` 的可追溯记录 | 推测 |

**红线**：不得因为代码实现了某种行为，就把它当成未来需求的正确业务规则；
也不得因为旧文档写过某种设计，就忽略代码已经变了。**两者都会导致「局部正确、整体错误」。**

## 三、领域文件元数据契约

每个领域文件顶部**必须**携带来源与新鲜度，否则读者无法判断它是否可信：

```markdown
> 来源：<权威源 + 具体位置> ｜ 最后确认：YYYY-MM-DD ｜ 适用范围：<边界> ｜ 状态：已核实
```

**状态语义**（三选一）：

| 状态 | 含义 | 可作依据？ |
|---|---|---|
| `已核实` | 已回源确认（对源码 / 对实测） | ✅ 可直接作为判断依据 |
| `待确认` | **有来源但尚未核实** | ⚠️ 可参考，必须同时标注不确定性；**不得静默升级为领域事实** |
| `已过时` | 已知与当前事实不符 | ❌ 保留用于追溯，**不得作为依据** |

**为什么必须有这一行**：知识库最大的风险不是缺少文档，而是**文档过期后以「看起来很可信」
的方式误导 AI**。没有新鲜度标记，过期知识比没有知识更危险。

## 四、漂移检测

**触发条件**（满足其一即检查）：

- 契约变更：ctt-server 端点 / DTO / 错误码变化
- 版本升级：`engines.vscode`、`@types/vscode`、依赖大版本
- **实测与记录不符**（最强信号）
- 关联仓库发生改动
- 周期性校准：**每个里程碑收尾时**校准一次

**动作**：

1. `git log` / `git diff` 确认变更来源（R10 变更溯源）
2. 回源核对，**就地改正**领域文件——不留过时判断（R15）
3. 当场无法确认的 → 标记 `状态：待确认` + 写明缺什么证据，**而不是删除或猜测**
4. 记录到 `activeContext.md`

**自动化边界**（重要）：

> 自动化只负责**发现变化、生成候选、阻止遗漏**；
> 契约语义、历史兼容理由这类高风险判断，**必须由人确认**后才写入领域文件。

不得让「代码变了」自动改写领域知识——工具守的是「代码变了，知识不能完全不变」的底线，
**语义判断仍然归人**。

## 五、领域清单

| 领域 | 范围 | 入口 |
|---|---|---|
| [`ai-workflow`](./ai-workflow/meta.md) | Agent 在本仓库如何工作：记忆维护、版本号、原子提交、验证证据、资源归属、只读边界 | `ai-workflow/meta.md` |
| [`sync-client`](./sync-client/meta.md) | 与 ctt-server 的同步引擎（**写路径**）：设备注册、pull/push、游标、LWW 冲突、批量原子性、幂等重试 | `sync-client/meta.md` |
| [`server-api`](./server-api/meta.md) | 服务端调用面（**读路径 + 通用约定**）：认证、响应与错误信封、错误码、限流与重试、统计端点消费 | `server-api/meta.md` |

**为什么是 3 个而不是照搬 ctt-server 的 4 个**：本仓库是**客户端**。ctt-server 把
`auth-lifecycle` 与 `api-contract` 分开，因为它同时**实现**认证流程与**产出** API 契约；
本仓库只**消费**两者，拆开会把「怎么调用服务端」切成两半、大量互相引用。故合并入 `server-api`。

## 六、生长规则

- **按需建档**：只在确有可复用知识时创建领域。空领域是违规，不是占位符——**宁可少而实**。
- **先归类**：新知识先判断归属领域，更新对应文件；无领域匹配才新建五件套。
- **就地改正**：领域文件**只写当前有效的结论**，不留版本流水账（那属于 `progress.md`）。
- **索引同步**：本文件的领域表必须与目录实际内容一致。
- **合并信号**：两个领域的 `principles.md` 若开始大面积重合，它们就是一个领域——合并。

领域名用 `kebab-case`，命名**能力或知识领域**而非文档类型。
