# sync-client — principles

> 来源：`../ctt-server` 的 `ConflictResolver` / `SyncPullService` / `SyncPushService` / `SyncCursorRepository`
> 最后确认：2026-09-15 ｜ 适用范围：同步引擎的不变量 ｜ 状态：**已核实**

## P1. 会话只有一个入口，且服务端是唯一权威

会话进入服务端**只能**经 `POST /api/v1/sync/push`。没有直接写入端点、没有导入端点、
没有批量 CSV。服务端 `SyncPushService` 是 `coding_sessions` 的唯一写入方。

推论：

- 客户端**不得**计算或上送任何时长/聚合值 —— 服务端用 `endTime - startTime` 自行推导
- 本地的统计只是**近似**；权威数字来自 `/api/v1/stats/**`（见 `../server-api` P7）
- 每次 push 成功后应拉回服务端状态以收敛（push → pull 的顺序由实践确定，见 `practices.md`）

## P2. 冲突解决是固定优先级链，服务端裁决

`ConflictResolver` 按序判断，**首个命中即返回**：

1. **删除胜出** —— 软删除状态胜过存活状态；两边都删则落到版本规则
2. **内容相同短路** —— 两边均为存活、且 `projectName`/`language`/`startTime`/`endTime`
   完全一致 → `KEEP_EXISTING`（幂等无操作，即使版本或时钟元数据漂移）
3. **服务端版本** —— 两边 `serverVersion > 0` → 高者胜
4. **客户端版本** —— 服务端版本相等，或任一边是全新提交（`serverVersion == 0`）→ 高 `clientVersion` 胜
5. **客户端修改时间** —— 客户端版本相等 → 晚的 `clientModifiedAt` 胜

**客户端义务**：每次本地修改都必须**递增** `clientVersion` 并更新 `clientModifiedAt`
（ISO-8601 UTC）。不递增 = 放弃在第 4/5 层的竞争力，修改可能被判定为不更新。

**另一项客户端义务**：服务端**不校验** `startTime < endTime`（仅 DB 有
`CHECK (end_time >= start_time)`），而 `start == end` 的退化行会被**所有统计端点静默跳过**。
客户端必须自行保证 `endTime > startTime`，否则数据入得了库、出不来统计。

**不要**在客户端实现自己的冲突合并逻辑 —— 服务端会裁决，本地的额外合并只会制造分歧。

## P3. dirty 标记是不可丢的状态

被标记 dirty 的会话表示「本地有服务端还不知道的修改」。丢失该标记 = 永久数据丢失
（下次同步不会推它）。

- push **成功**后才能清除；失败必须保留（安全重试的前提）
- 应用拉取结果时：**dirty 的本地行不被覆盖**（本地未推送的编辑优先），
  服务端版本在下次 push 后被 LWW 裁决

*参考实现的经验*：`SyncSessionApplier` 对拉取结果分五种结局 ——
创建 / 覆盖（本地干净）/ 跳过（本地 dirty）/ 软删除（本地干净）/ 保留（本地 dirty）。

## P4. 游标只增不减，客户端永不回退服务端

有效查询位置是 `max(服务端 watermark, 客户端游标)`。一个陈旧的客户端**无法**让服务端
重新投递它认为已消费的变更。

- 持久化的是 **pull 响应里的 `nextCursor`**，不是「最后应用的那条 `changeId`」，
  也**不是** push 响应的 `nextCursor`（见 P9）
- 游标存储必须单调：写入时取 `max(已有, 新值)`
- 账号切换时必须**清空**游标（否则新账号会从旧账号的位置开始拉）

## P5. push 整批原子；幂等优于恰好一次

- 一个请求在一个事务内落地：要么整批成功（会话 + change log），要么全不落地。
  2xx 因此是**安全的重试点**，也可以放心标记该批为已同步
- 幂等规则：重复推相同内容 = 无操作；删除服务端从未有过的会话 = 无操作；
  无新变更的 pull 返回空数组 + 当前游标
- **不要**用「客户端意图登记」去抑制重复 —— 协议本身就是为安全重试设计的

**批量上限是客户端自律**：服务端 push 请求只有「非空」校验，没有条目上限
（1000 只存在于 pull 侧）。参考实现用 500 一批，超出时自行分批。

## P6. origin device 与 last-writer 是两件事

- `origin_device_id` = **谁首次创建**该会话，创建时写入、**永不重写**
- `updated_by_device_id` = 谁最后写入

按设备维度的统计**必须**用 origin —— last-writer 会漂移到「恰好编辑过它的那台设备」，
让会话从原设备的数据里消失。这是参考实现实际修过的 bug。

推论：本仓库若采用既有本地会话，它们会**永久归属原设备**（可能是 JetBrains 插件）。
这是设计，不是缺陷。

## P7. 设备注册是授权前置，且自愈路径是重注册

未注册（或已吊销）的设备无法 pull/push。**未知、他人、已吊销一律返回 `404 COMMON_002`，
从不返回 403** —— 有意为之，避免设备存在性泄漏。

- 首次运行必须注册；`deviceId` 由客户端生成（UUIDv4），一次生成、持久化、跨重启不变
- 收到 `404 COMMON_002` → **重新注册同一个 `deviceId`** 即可清除吊销状态（服务端
  `setRevokedAt(null)`），这是自愈路径
- 重注册不要换 UUID：换了会失去游标归属与 origin 归因

## P8. 服务端 watermark 是权威但乐观的

watermark 在**页面生成时**推进，而不是客户端确认应用后。客户端在收到页面后崩溃会
永久错过该页（对该设备而言）。

这是**已接受的取舍**，不是待修 bug：

- 不要试图让客户端回退 watermark —— 单调守卫的存在就是为了阻止重复投递风暴
- 真正的修复需要「客户端确认游标」协议，属服务端变更（走需求报告流程）
- 分页把暴露面从「整个响应」缩小到「一页」
- 会话数据仍在服务端，下次有人写这些会话时会重新收敛

## P9. 变更日志是拉取的唯一真相来源

`change_id` 是**唯一**的排序保证。不要把它当作计数（它是全库共享的 BIGSERIAL），
也不要复用、不要回填时间戳参与排序决策。

- 对客户端而言它是**不透明游标**
- **游标只由 pull 响应推进。** push 响应里的 `nextCursor` 是「该用户当前的**最大** changeId」，
  位置在本次 push 写下的 change **之后**——**不得**用作 pull 起点，
  否则会恰好跳过本次 push 的变更（含服务端对你的裁决），客户端**永不收敛**。
  详见 `practices.md` 的同步循环红线

## P10. 客户端只转发事实，不做语义转换

本插件的职责是**如实记录、原样上报**，不是「把数据整理得更漂亮」。

| 数据 | 客户端做什么 | 谁负责转化 |
|---|---|---|
| 语言 | 原样发送 `document.languageId`（`typescript`） | **服务端**：归一化到 GitHub Linguist 规范名（读取时） |
| 时长 | **不计算、不发送** | 服务端由 `endTime - startTime` 推导 |
| 时区 | 发送 UTC 绝对时刻 | 服务端按调用方 `timezoneOffset` 分桶 |
| 本地 schema | **不迁移、不加列** | 插件端（`MigrationManager`） |

**红线：本地不得自建映射表或词表。** 服务端既已在读取时归一化，本地做任何转换
都只是制造与服务端打架的数据；而两端各持一套规则，**必然漂移**。

**推论**：看到「语言名不好看/大小写不一致」时，正确的动作**不是**在本地修，
而是**什么都不做**——原样转发。展示层需要可读名时，在**展示时**映射。

> **术语提醒**：本表第 1 行的「归一化」专指**语言名**；`../server-api` P4 里的
> 「归一化」指的是**时长语义**（把 accumulate 并成 merge，那是缺陷）。
> **两个含义互不相干，本仓库内禁止裸用「归一化」**——必须点名是哪一个（见
> [`../server-api/meta.md`](../server-api/meta.md) 元语表）。
