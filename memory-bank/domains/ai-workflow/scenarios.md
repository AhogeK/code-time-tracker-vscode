# ai-workflow — scenarios

触发 → 判断 → 动作。

## S1. 会话开始

1. 读 `memory-bank/` 全部（projectbrief / techContext / systemPatterns / activeContext / progress）。
2. 读 `AGENTS.md` 规则 —— 它们是**约束**，不是背景资料。
3. 识别适用**领域**，读该领域 `meta.md` → 任务需要的那份文件。
4. 之后才规划。跨 3 步以上或触及 >5 个文件，**先写计划再动代码**。

跳过第 3 步是同一个错误被重犯的方式：规则说「不要 X」，而**为什么**与已否决的替代方案在领域文件里。

## S2. 改动代码

1. 先读完整文件（R23）—— 片段阅读产出的局部修复会破坏全局不变量。
2. 匹配现有模式；**不要**在已有约定旁引入第二套约定（R11）。
3. 按 P3 验证 —— 证据类型匹配变更性质。
4. 同一轮内更新 `package.json` 版本号（R17）与时间线层（R2）。
5. **停**。报告状态，等提交指令。

## S3. 提交

仅由明确的提交/推送指令触发（P2）。

1. 字面搜索本回合用户消息里的 `提交` / `commit` / `推送` / `push` —— 未命中即禁止提交（R6 机械判定法）。
2. 检视 diff；确认没混入敏感或无关内容。
3. 拆成原子提交：**代码**（一个连贯变更）→ **版本号** → **记忆**（R7）。
4. 提交信息：约定式前缀，subject ≤72 字符，body 说明**为什么**。
   **绝不**添加 AI 署名或 co-author 页脚。
5. 先在 `develop` 提交；`master` 只接受逐个 cherry-pick 的非 AI 提交（**永不**整分支合并）。
6. 收尾：两个分支都已推送且干净，工作树回到 `develop`。

## S4. 收到关于刚交付内容的反馈

1. 当成**报告**处理（P7）：改任何东西之前先取证据 —— 测量当前行为（实际输出、日志、截图），
   不要从意图出发辩护。
2. 区分两种失败：**方向错了** vs **执行错了**。修法相反，猜错浪费一轮。
3. 用户提出某个方向（「用统一渐变」「加内部滚动」）要认真对待 ——
   一个曾被否决的建议再次出现，说明当时的否决是错的。
4. 修复有取舍时**说出取舍**，不要默默选一个。

## S5. 「这边做不到」

1. 先用两次对照实验确认（不要先假设）。
2. 确实是能力缺口 → 写**需求报告**（`./<topic>-requirement.md`，五段齐全），交给用户（R3）。
   不要伪造、不要在本仓库绕过去硬凑、不要碰关联仓库。
3. 同时让本仓库对限制**诚实**（注释/README 说明），而不是悄悄不一致。

## S6. 一轮结束后的知识维护

1. 分类：这是持久事实、决策规则、坑，还是仅近期历史？
   - 持久 → 领域文件（`principles` / `scenarios` / `practices` / `references`）
   - 近期 → `activeContext.md`
   - 里程碑 → `progress.md`
   - 无新知识 → **什么都不记**（不要灌水）
2. 主题已存在则**更新原条目**，绝不追加第二个互相竞争的版本。
3. 检查行数上限，超限时按 R15 的归档流程处理。

## S7. 文件超出限额

1. 按性质拆分：**持久判断** → 领域；**历史** → `memory-bank/archives/YYYY-MM-DD-<name>.md`；
   **状态** → 一段简短现状。
2. 重写该文件为「状态 + 主题摘要 + 横切教训」。
3. 更新末尾的归档指引行，保证链路可追溯。
4. 完整性校验：归档前后总行数差 = 新归档文件头行数。

**注意**：文件超限但无超期条目时，**不得**为此归档热数据，也**不得**删内容 ——
先压缩措辞，再考虑把已完结的成组条目移入归档（R15）。

## S8. 启动 / 停止后台资源

- 长驻服务（`pnpm run watch`、Extension Development Host、`vscode-test` 宿主）：
  **后台静默启动**，日志走控制台 / Output Channel —— **不要**重定向到文件（R13）。
  唯一的例外是确有必要留痕时，R13 允许的长期服务日志文件，且**任务结束必须删除**。
- **绝不让命令挂起等输出**：前台等待会让整轮卡住。
- 收尾：按命令**行**匹配自己启动的进程再停；**不要**凭端口或记忆中的 PID 杀进程。
- 临时配置/令牌/载荷：删除。持久助手（测试账号、脚本）：保留并复用。

## S9. 某个被跟踪文件显示已修改，但你没编辑过

症状：`git status` 列出你从未打开的文件 —— 当前仓库的典型嫌疑人是
`pnpm-workspace.yaml`（出现 `<package>: set this to true or false` 之类占位），
随后 `git checkout` 因该文件有本地改动而拒绝执行。

那是 **pnpm 的占位符**，不是谁的编辑。避免与处理：

1. `git checkout -- <file>` 恢复，然后重试原本要做的 checkout。
2. 本仓库已在 `pnpm-workspace.yaml` 固定 `allowBuilds` 决策，降低触发概率。
3. 确实需要批准新的构建脚本 → `pnpm approve-builds`，**那次是真的配置变更**，可以提交。
4. **不要在历史提交上跑包管理脚本**：`node_modules` 共享而 workspace 配置按提交，二者不匹配时
   pnpm 会改写该文件。
