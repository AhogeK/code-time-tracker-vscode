## Boundary

Agent 在**本仓库内**如何工作：知识存在哪、怎么保证不漂移、工作如何被版本化与提交、如何被验证、
允许触碰什么。本领域讲**工作过程**，不讲产品。

**In scope**：记忆/知识维护、版本管理、提交粒度、分支政策、验证证据、资源归属、只读边界。

**Out of scope**：

- 扩展本身的架构约定 → [`systemPatterns.md`](../../systemPatterns.md)
- 如何与后端交互 → [`server-api`](../server-api/meta.md)
- 同步引擎实现 → [`sync-client`](../sync-client/meta.md)
- 规则条文本身（在 `AGENTS.md`）—— 本领域承载规则**背后的实践与陷阱**，以及让规则站得住的理由

## 元语与消歧

**先消歧，再检索。** 本领域的词看着都懂，但**误读的代价是流程性错误**（如把提问当指令、
把修复当授权）。下表左列是本仓库的确定含义，右列是**必须区分**的近似说法。

### 核心对象

| 元语 | 本领域的确定含义 | 别名 / 口语 | **非同义词（必须区分）** |
|---|---|---|---|
| **时间线层** | `memory-bank/` 顶层 5 文件，回答「最近发生了什么」 | 「记忆」「memory」 | **领域层** —— 持久判断，不随时间失效（P4） |
| **领域层** | `memory-bank/domains/` 五件套，回答「这里什么是真的」 | 「知识库」 | 时间线层；**也不是 changelog**（P5） |
| **横切规范** | 适用于所有模块的约定 → `systemPatterns.md` | 「规范」 | 领域专属判断 —— 重复即会漂移（P6） |
| **原子提交** | 一个 commit 一件事，可独立理解与回滚 | 「小提交」 | **「拆得越细越好」不是它的含义** —— 过细无意义，同意图的多文件可合并 |
| **验证证据** | 测量值 / 实际运行输出 / 截图 | 「测过了」 | **类型检查通过** —— 对 VS Code 集成而言「能编译 ≠ 能跑」（P3） |
| **提交授权** | 用户在本回合明确说出的 `提交` / `commit` / `推送` / `push` | 「同意了」 | 「可以」「没问题」「审查通过」「继续」—— **都不算**（P2） |
| **授权闭合** | 授权在指名变更提交完毕后**立即失效** | 「他说要提交」 | 「提交并推送，然后继续做 X」**不授权** X 完成后提交（P2） |
| **归因漂移** | 用「这应该是错的」掩盖「用户改过」 | 「记忆过时了」 | 真正的记忆过期 —— 先 `git log` 判断是哪种（P10） |

### 边界

- 本领域**只讲过程**，不讲产品；产品语义在 `../server-api` 与 `../sync-client`
- **规则条文在 `AGENTS.md`**，本领域承载规则背后的**实践与陷阱**，以及让规则站得住的理由
